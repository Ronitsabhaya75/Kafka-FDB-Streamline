# Research: Protobuf Schema Design & Tooling Validation

## Summary

This document reviews and validates the core Protocol Buffers (Protobuf) schema proposed in [Proposal.md](../Proposal.md), investigates tooling for code generation and schema governance, evaluates Python runtimes, and defines the schema evolution strategy for the **FoundationDB-to-Kafka Streamline** connector.

### Key Architectural Recommendations
1. **Compilation & Schema Governance:** Adopt **`buf`** as the primary build tool and linter, while maintaining a pure Python fallback via **`grpcio-tools`** in automated environments.
2. **Python Runtime:** Use the official **`google.protobuf`** runtime (v5.x/v4.x) with Python type stubs (`.pyi`). Reject `betterproto` due to its lack of Confluent Schema Registry compatibility and pure-Python serialization performance bottlenecks.
3. **Schema Enhancements:**
   - Extend `FDBSingleKeyMutation.MutationType` to enumerate all 14 FoundationDB atomic mutation types defined in `fdb_c.h`.
   - Add a high-throughput **`FDBMutationBatch`** payload envelope to prevent Kafka per-record serialization overhead when streaming high-velocity transaction batches.
   - Adopt semantic package namespacing (`fdb.kafka.cdc.v1`) adhering to Google and Buf API style standards.
   - Ensure full wire-format alignment with Confluent Schema Registry (framing header: magic byte + 4-byte schema ID + message indexes).

## 1. Core Schema Review

The schema presented in `Proposal.md` (Section 3) models versioned FDB mutations and boundary markers. Below is an itemized evaluation of each core message type:

### 1.1 `FDBVersionIndex`
```protobuf
message FDBVersionIndex {
    uint64 fdb_version = 1;
    uint32 sequence_no = 2;
}
```
- **Validation:** 
  - `fdb_version`: FoundationDB commit versions are monotonically increasing 64-bit integers generated by the cluster coordinators (~1,000,000 increments/sec). `uint64` is the exact representation needed.
  - `sequence_no`: FoundationDB mutations within a single commit version and proxy are assigned sequential order numbers. `uint32` allows up to 4.29 billion mutations per version, comfortably exceeding FDB's transaction limit (10,000 mutations / 10MB per transaction).
- **Verdict:** Valid as designed.

---

### 1.2 `VersionEnd`
```protobuf
message VersionEnd {
    uint64 fdb_version = 1;
}
```
- **Validation:** 
  - FDB native CDC streams emit a stream boundary marker signaling that all mutations for a commit version have been yielded. Downstream consumers require this marker to advance transactional watermarks.
- **Proposed Enhancement:** Add `uint32 total_mutations = 2;` and `google.protobuf.Timestamp commit_timestamp = 3;`. This allows downstream stream-processing engines (e.g., Apache Flink, Kafka Streams) to verify batch completeness and calculate end-to-end ingestion lag without inspecting external metadata.

---

### 1.3 `FDBSingleKeyMutation`
```protobuf
message FDBSingleKeyMutation {
    enum MutationType {
        SET = 0;
        ADD = 1;
        // ...
    }
    bytes key = 1;
    bytes value = 2;
    MutationType mutation_type = 3;
}
```
- **Validation & Deficiencies:**
  1. **Proto3 Enum 0-Value Principle:** In Proto3, field tag 0 of an enum must represent an unspecified default value (e.g., `MUTATION_TYPE_UNSPECIFIED = 0`) to prevent accidental default deserialization when fields are omitted.
  2. **Incomplete Mutation Types:** `Proposal.md` only enumerates `SET` and `ADD`. In reality, FoundationDB's C API (`fdb_c.h` line 194) defines 14+ distinct atomic operations that appear directly in CDC streams.
- **Proposed Fix:** Enumerate all atomic types from `fdb_c.h`:
  - `SET_VALUE = 1`
  - `ADD_VALUE = 2`
  - `AND = 3`
  - `OR = 4`
  - `XOR = 5`
  - `MAX = 6`
  - `MIN = 7`
  - `BYTE_MIN = 8`
  - `BYTE_MAX = 9`
  - `SET_VERSIONSTAMPED_KEY = 10`
  - `SET_VERSIONSTAMPED_VALUE = 11`
  - `COMPARE_AND_CLEAR = 12`
  - `APPEND_IF_FITS = 13`

---

### 1.4 `FDBClearRange`
```protobuf
message FDBClearRange {
    bytes begin_key = 1;
    bytes end_key = 2;
}
```
- **Validation:** 
  - FoundationDB clear ranges operate over half-open intervals: `[begin_key, end_key)`.
  - Representing keys as `bytes` is mandatory because FDB keys are arbitrary binary byte sequences (often encoded with FDB Tuple or Subspace layers).
- **Verdict:** Valid as designed.

---

### 1.5 `FDBMutation` & `FDBMutationRecord`
```protobuf
message FDBMutation {
    FDBVersionIndex version_index = 1;
    oneof mutation {
        FDBSingleKeyMutation single_key_mutation = 2;
        FDBClearRange clear_range = 3;
    }
}

message FDBMutationRecord {
    string stream_name = 1;
    oneof record {
        FDBMutation mutation = 2;
        VersionEnd version_end = 3;
    }
}
```
- **Validation & Throughput Bottleneck:**
  - When FDB writes transactions under moderate-to-high load (e.g., 50,000 mutations/sec), producing **one individual Kafka message per mutation** introduces crippling overhead:
    - High per-message Kafka broker request rate and metadata overhead.
    - Massive CPU overhead in serialization and network framing.
- **Proposed Fix:** Introduce an optional batch container **`FDBMutationBatch`** containing `repeated FDBMutation mutations = 3;`. This preserves full backwards compatibility with single-mutation envelopes while granting 10x–50x higher Kafka publishing throughput when streaming large batches.

## 2. Protobuf Compilation Tooling Evaluation

We evaluated the three primary options for compiling `.proto` definitions into Python artifacts:

| Feature / Criteria | `protoc` (Official C++ Compiler) | `grpcio-tools` (Python Pip Package) | `buf` (Bufbuild CLI Tooling) |
| :--- | :--- | :--- | :--- |
| **Installation Mechanism** | OS Binary (Homebrew, APT, GitHub Zip) | `pip install grpcio-tools` | OS Binary (Homebrew, GitHub Release) |
| **Linting & Style Guide Enforcement** | ❌ None (Requires separate linters) | ❌ None | ✅ Built-in (`buf lint` with standard rule presets) |
| **Breaking Change Detection** | ❌ None | ❌ None | ✅ Built-in (`buf breaking --against .git#branch=main`) |
| **Dependency & Import Management** | ⚠️ Manual include paths (`-I`) | ⚠️ Manual include paths (`-I`) | ✅ Automatic via `buf.yaml` module roots |
| **Python Stub Generation (`.pyi`)** | ✅ Requires `--pyi_out` flag | ⚠️ Requires extra invocation | ✅ Automated in `buf.gen.yaml` |
| **Remote Plugin Support** | ❌ Manual plugin installation | ❌ Only built-in grpc plugin | ✅ Remote plugin registry (no local protoc plugins required) |
| **CI/CD Integration** | Basic bash script | Pure Python `python -m grpc_tools.protoc` | Native GitHub Action (`buf-setup`, `buf-lint`) |

### Tooling Recommendation: **`buf` (Primary) + `grpcio-tools` (Fallback)**
- **Why `buf` wins:**
  - Prevents breaking changes automatically in CI before pull requests are merged.
  - Standardizes Protobuf directory hierarchy, package naming, and field naming.
  - Eliminates the need to maintain cumbersome local `protoc` binary installations on developer machines.
- **Role of `grpcio-tools`:** Retained as a secondary fallback script in local environments where developers cannot install external binaries.

## 3. Python Protobuf Runtime Evaluation

Once `.proto` files are compiled into Python modules, they must be executed by a Python runtime. We evaluated the two leading Python libraries:

| Evaluation Metric | `google.protobuf` (Official Google Runtime) | `betterproto` (Dataclass Alternative) |
| :--- | :--- | :--- |
| **Architecture** | C++ / `upb` micro-engine backend with Python wrapper | Pure Python generated `@dataclass` classes |
| **Serialization Speed** | **Extremely Fast** (native C / upb bindings) | **Slow** (pure-Python reflection & serialization) |
| **Memory Footprint** | Low (efficient C-allocated memory) | Moderate (Python object overhead per dataclass) |
| **Type Hints & Autocomplete** | ✅ Full `.pyi` type stubs generated by protoc | ✅ Native Python dataclass annotations |
| **Confluent Schema Registry** | ✅ Supported natively by `confluent-kafka[protobuf]` | ❌ Incompatible (Confluent expects `google.protobuf.message.Message`) |
| **Maintenance & Longevity** | Maintained directly by Google / Protobuf team | Community-maintained (slower release cadence, open issues with `oneof`) |
| **Complex `oneof` Handling** | Robust (via `WhichOneof()`, explicit field checks) | Known edge-case bugs in complex nested unions |

### Runtime Recommendation: **`google.protobuf` (Mandatory)**
- **Rationale:** 
  1. **Throughput:** A CDC connector streaming tens of thousands of mutations per second will spend substantial CPU cycles in serialization. Official `protobuf` with its C++/upb backend is up to **20x–50x faster** than pure Python dataclass implementations.
  2. **Ecosystem Compatibility:** `confluent-kafka`'s built-in `ProtobufSerializer` and `ProtobufDeserializer` strictly require instances of `google.protobuf.message.Message`. Using `betterproto` would require writing bespoke translation shims.

## 4. Schema Evolution & Compatibility Rules

Protobuf achieves high performance and forward/backward compatibility through **field tags (numbers)** rather than field names. When streaming FDB CDC mutations into Kafka topics consumed by heterogeneous microservices, the following rules must be strictly enforced:

### 4.1 Backward Compatibility Rules (Old Consumer reads New Message)
- **Rule 1: Never change existing field tag numbers.** Field numbers (e.g., `uint64 fdb_version = 1;`) are encoded on the wire. Changing a tag from `1` to `2` completely corrupts deserialization.
- **Rule 2: Never change the wire type of an existing field.** For example, changing `uint32` to `string` or `bytes` breaks the binary framing.
- **Rule 3: Adding new fields is always safe.** Proto3 preserves unknown fields during deserialization and re-serialization. Older consumers reading records produced with new fields will simply ignore the new tags.

### 4.2 Forward Compatibility Rules (New Consumer reads Old Message)
- **Rule 4: Never make an optional field required.** (Proto3 does not support `required` by design).
- **Rule 5: Always account for default values.** If a new consumer reads an old record where a new field is absent, it receives the proto3 default (`0`, `""`, `b""`, `false`).

### 4.3 Safe Deletion & Reservation Rules
- **Rule 6: Never reuse deleted tags or names.** If a field like `stream_name = 1` is retired, it must be marked as `reserved`:
  ```protobuf
  reserved 1;
  reserved "stream_name";
  ```
  This prevents a future developer from assigning tag `1` to a different field, which would silently corrupt historical Kafka event replay.

### 4.4 Enum Evolution Rules
- **Rule 7: Never change existing enum numeric values.** 
- **Rule 8: Always maintain 0 as `_UNSPECIFIED`.** If an older consumer receives a newly added enum value, proto3 treats it as an unknown enum integer rather than throwing an exception.

## 5. Kafka & Confluent Schema Registry Integration

When publishing Protobuf messages to Apache Kafka, applications can publish raw Protobuf bytes or publish via the **Confluent Schema Registry**.

### 5.1 Confluent Wire Format Framing
The Confluent Schema Registry defines a standardized 5-byte framing envelope prepended to the raw Protobuf binary payload:

```
┌─────────────────┬────────────────────────────┬─────────────────────────────┬───────────────────────────┐
│ Magic Byte (1B) │ Schema ID (4 Bytes, Big-E) │ Message Index Array (varint)│ Protobuf Serialized Bytes │
│     0x00        │         e.g., 0x00000004   │     e.g., [0] (Root msg)    │    <payload binary>       │
└─────────────────┴────────────────────────────┴─────────────────────────────┴───────────────────────────┘
```

1. **Magic Byte (Byte 0):** Always `0x00` (identifies Confluent framed serialization).
2. **Schema ID (Bytes 1–4):** 32-bit unsigned integer in network byte order identifying the registered schema in Schema Registry.
3. **Message Index Array:** Variable-length zigzag varint array indicating the target message type within a multi-message `.proto` file (e.g., index `0` selects `FDBMutationRecord`).
4. **Protobuf Payload:** Standard Google Protobuf wire binary.

### 5.2 Compatibility Modes
When configuring Confluent Schema Registry for FDB CDC topics:
- **Recommended Mode: `BACKWARD_TRANSITIVE`**
  - Ensures any new schema version can successfully read data written by **all** previous versions in the Kafka topic.
  - Prevents breaking consumers during rolling cluster deployments.

## 6. Proposed Enhanced Schema (`fdb_cdc.proto`)

Below is the validated, enhanced Protobuf definition addressing all findings from the proposal review:

```protobuf
syntax = "proto3";

package fdb.kafka.cdc.v1;

import "google/protobuf/timestamp.proto";

option go_package = "github.com/Ronitsabhaya75/Kafka-FDB-Streamline/gen/go/fdb/kafka/cdc/v1;cdcv1";
option java_multiple_files = true;
option java_package = "com.fdb.kafka.cdc.v1";

// Tracks an FDB commit version and mutation sequence number within that version.
message FDBVersionIndex {
    // 64-bit monotonically increasing FDB commit version
    uint64 fdb_version = 1;

    // Sequence number within the commit version (differentiates ordered mutations)
    uint32 sequence_no = 2;
}

// Emitted at version boundaries to signal that all mutations for an FDB version are complete.
message VersionEnd {
    // The FDB commit version that has concluded
    uint64 fdb_version = 1;

    // Optional total count of mutations emitted in this version (for stream auditing)
    uint32 total_mutations = 2;

    // Wall-clock timestamp when the version was processed/committed
    google.protobuf.Timestamp commit_timestamp = 3;
}

// Represents single key mutations, including standard writes and atomic operations.
message FDBSingleKeyMutation {
    // Maps 1:1 with FoundationDB native atomic mutation types in fdb_c.h
    enum MutationType {
      FDB_CDC_MUTATION_TYPE_SET_VALUE = 0,
      FDB_CDC_MUTATION_TYPE_CLEAR_RANGE = 1,
      FDB_CDC_MUTATION_TYPE_ADD = 2,
      FDB_CDC_MUTATION_TYPE_AND = 6,
      FDB_CDC_MUTATION_TYPE_OR = 7,
      FDB_CDC_MUTATION_TYPE_XOR = 8,
      FDB_CDC_MUTATION_TYPE_APPEND_IF_FITS = 9,
      FDB_CDC_MUTATION_TYPE_MAX = 12,
      FDB_CDC_MUTATION_TYPE_MIN = 13,
      FDB_CDC_MUTATION_TYPE_SET_VERSIONSTAMPED_KEY = 14,
      FDB_CDC_MUTATION_TYPE_SET_VERSIONSTAMPED_VALUE = 15,
      FDB_CDC_MUTATION_TYPE_BYTE_MIN = 16,
      FDB_CDC_MUTATION_TYPE_BYTE_MAX = 17,
      FDB_CDC_MUTATION_TYPE_MIN_V2 = 18,
      FDB_CDC_MUTATION_TYPE_AND_V2 = 19,
      FDB_CDC_MUTATION_TYPE_COMPARE_AND_CLEAR = 20
    }

    // Target key in FoundationDB
    bytes key = 1;

    // Target value or operand for atomic mutations
    bytes value = 2;

    // Operation type
    MutationType mutation_type = 3;
}

// Represents a range clear operation over [begin_key, end_key).
message FDBClearRange {
    // Inclusive start key of the range
    bytes begin_key = 1;

    // Exclusive end key of the range
    bytes end_key = 2;
}

// Union of individual mutation operations tagged with a version index.
message FDBMutation {
    // Monotonic ordering coordinates
    FDBVersionIndex version_index = 1;

    // Mutation operation payload
    oneof mutation {
        FDBSingleKeyMutation single_key_mutation = 2;
        FDBClearRange clear_range = 3;
    }
}

// High-throughput container for batching multiple mutations into a single Kafka payload.
message FDBMutationBatch {
    // Monotonically ordered mutations within this batch
    repeated FDBMutation mutations = 1;

    // Optional stream identifier
    string stream_name = 2;
}

// Top-level Kafka record envelope.
message FDBMutationRecord {
    // Directory or CDC stream identifier
    string stream_name = 1;

    // Ingestion or transaction commit timestamp
    google.protobuf.Timestamp timestamp = 2;

    // Record payload
    oneof record {
        FDBMutation mutation = 3;
        VersionEnd version_end = 4;
        FDBMutationBatch batch = 5;
    }
}
```

## 7. Developer Workflow & Build Commands

### 7.1 Using `buf` (Recommended)

#### Configuration Files

**`buf.yaml`** (Module Root):
```yaml
version: v2
modules:
  - path: proto
lint:
  use:
    - DEFAULT
  except:
    - PACKAGE_VERSION_SUFFIX
breaking:
  use:
    - FILE
```

**`buf.gen.yaml`** (Code Generation):
```yaml
version: v2
plugins:
  - remote: buf.build/protocolbuffers/python
    out: gen/python
  - remote: buf.build/protocolbuffers/pyi
    out: gen/python
```

#### CLI Execution Commands
```bash
# 1. Lint schema against standard Protobuf style rules
buf lint

# 2. Check for backwards-incompatible breaking changes against main branch
buf breaking --against '.git#branch=main'

# 3. Generate typed Python source code (_pb2.py and _pb2.pyi)
buf generate
```

---

### 7.2 Using `grpcio-tools` / `protoc` (Fallback)

If `buf` is not installed, developers can generate the exact same Python artifacts using standard `pip` packages:

```bash
# Install compilation tooling and type-stub generator
pip install grpcio-tools mypy-protobuf

# Compile .proto into Python with type annotations
python -m grpc_tools.protoc \
    -Iproto \
    --python_out=gen/python \
    --pyi_out=gen/python \
    proto/fdb/kafka/cdc/v1/fdb_cdc.proto
```
